# Conversations, store updates and delivery addresses

## Customer workflow

Normal account registration/sign-in prepares private messaging automatically. **Account → Your inbox** opens support conversations without a recovery file, extra passphrase or manual unlock. Start a conversation, send your question, and return for replies. The buyer and store can continue until satisfied, mark resolved, or reopen; sending a new reply reopens a resolved conversation. History loads in bounded pages. Unread badges and a content-free in-app notification refresh on focus and every 30 seconds; open conversations refresh every 15 seconds while visible. **Store updates** keeps announcements separate and exposes promotion preferences.

An already signed-in account when this feature first arrives may need normal sign-in once to synchronize its private messaging identity. No customer recovery-key workflow exists. A fresh device uses normal account sign-in to retrieve and decrypt the account’s encrypted key backup. A non-extractable private CryptoKey is remembered in origin-scoped IndexedDB; signing out removes the remembered key on that device. If storage is blocked, the active sign-in can use memory; after a page reload it may need normal sign-in again. HTTPS and browser Web Crypto are required.

Guest contact submissions from the earlier contact form remain one-way encrypted intake, available under **Admin → Inbox**. Registered customers are directed to the new two-way account inbox. Old anonymous messages cannot be retroactively converted to two-way conversations: they have no authenticated sender identity or return encryption key. The contact page explains the account-inbox option.

## Administrator workflow

**Admin → Inbox** retains the original store-key setup and anonymous intake. **Admin → Conversations** handles two-way threads. Import the existing store recovery file and passphrase to decrypt and reply. New threads use the active store key; each existing thread retains its original recipient key, so retain older store backups after rotation. The API limits customers to 20 unresolved threads and each thread to 10,000 messages; message text is bounded at 5,000 characters in the official clients.

**Admin → Broadcasts** provides a draft composer, optional uploaded image, safe internal destination link, preview, edit, publish and archive. Publishing makes a message available to accounts registered at that time, without an unbounded per-user fan-out transaction. Business announcements reach all such registered accounts; promotions respect the customer’s current offer preference. Read state belongs to each account. Published content cannot be edited; archive it and publish a replacement. This release sends in-app messages, not email/SMS or device push. Merely deploying the feature publishes no announcement.

## Encryption and account-key handling

Support message bodies are encrypted in the sending browser with a fresh AES-256-GCM key and nonce. The AES key is wrapped independently to the customer and store RSA-OAEP-3072 public keys. Version 2 authenticated additional data binds message ID, conversation ID, sender ID and both recipient key IDs. Both participants can decrypt their sent and received history. APIs validate envelope shape, enforce ownership and participant identities, serialize concurrent sends, assign monotonically increasing message sequences and advance read markers without moving backwards. Retries reuse the exact envelope ID/bytes. No unencrypted private key or support message plaintext is submitted to the messaging endpoints. Store-managed recovery, described below, can recover customer messaging keys. Public keys, conversation membership, timestamps, status and unread/read markers are visible metadata.

For seamless customer access, the browser encrypts its private JWK using an AES-GCM key derived from the normal sign-in password by PBKDF2-SHA256 (600,000 iterations, random salt). Only the encrypted backup is stored by the messaging service and only its owner can fetch it. Passwords and decrypted JWKs are not persisted by the browser. The current authentication service does receive the account password for normal password verification: this is **not a zero-knowledge authentication protocol**, and password wrapping does not protect against a malicious authentication server observing a login. HTTPS, authentic served JavaScript, trusted authentication and recipient keys remain required. This implementation does not provide forward secrecy or an independent security audit. Store recovery passphrases stay browser-only. Announcements are ordinary administrator-authored content, not private encrypted support messages.

### Forgotten passwords and managed recovery

The sign-in screen links to **Forgot password?**. Reset requests return the same accepted response for known/unknown emails when mail delivery is configured. A 256-bit random link token is stored only as a SHA-256 digest, expires in 30 minutes, and is consumed once in the same transaction as the password replacement. The token travels in the email URL fragment and is removed from browser history after loading; it is not part of HTTP access logs or referrer URLs. Password confirmation is checked in the browser. Request limits apply per account and IP. A successful reset revokes all older JWT sessions through a database-backed session version, invalidates other outstanding reset links, and records an audit event. Normal sign-in remains required after a reset.

**The owner explicitly chose store-managed message recovery** so customers need neither recovery files nor the previous password after a reset. During normal registration/sign-in, the browser also encrypts its private JWK to the recovery service’s RSA public key, using a fresh AES-GCM key and a context binding to account ID and messaging key ID. The database stores that opaque envelope. The recovery service’s private key is separately encrypted at rest with a stable deployment secret. On a verified password reset, the service unwraps the account key and re-encrypts the ordinary customer backup under the new password, preserving all existing conversation ciphertext and key IDs. The old password no longer unlocks the new backup. **The recovery service can access customer messaging keys and therefore private customer conversation content.** This intentionally relaxes server-blind E2EE to provide the seamless recovery the owner selected. Administrative/anonymous inbox recovery keys are not escrowed by this customer mechanism.

Use a stable `MESSAGE_RECOVERY_SECRET` of at least 32 random characters on the API. If omitted, the service derives a purpose-specific wrapping key from `JWT_SECRET`. Configure a dedicated secret before the first managed recovery key is created if separation from JWT rotation is required. Keep the secret backed up with the deployment’s secure secret process. Never change the effective secret without re-encrypting the stored recovery private key first; losing it makes managed recovery unavailable. Normal password-encrypted login backups remain separate. The recovery private key and decrypted customer JWK are never exposed by public API responses or logs.

Accounts with messaging keys created before managed recovery must perform normal sign-in once to backfill their encrypted recovery envelope. A password reset for an unsynced legacy inbox fails safely with a support message rather than silently replacing its key or destroying history. Old anonymous messages cannot be recovered by resetting a customer password because they were encrypted solely for the administrator.

### Email delivery setup

Configure `RESEND_API_KEY` and `EMAIL_FROM` with a verified sender/domain on both API and independent worker. For the combined Render staging service, both processes inherit its environment variables. Set `STOREFRONT_ORIGIN` to the storefront’s real HTTPS origin. No email credential is exposed through `NEXT_PUBLIC_` variables. Without mail configuration, reset requests fail uniformly with an explicit service-unavailable message; no account-existence detail is disclosed.

A database-backed encrypted email outbox decouples requests from the provider. Workers claim rows with leases and `SKIP LOCKED`, send through a fixed Resend API URL with an idempotency key, retry transient failures up to five attempts, and discard expired/consumed links. Ciphertext payloads are cleared after delivery or permanent failure. Queue encryption uses a domain-separated key derived from `JWT_SECRET`; rotate only after pending reset emails drain or expire. Deploying this code sends no email until someone requests a reset. Automated tests use fake delivery and never send real customer email. Provider delivery in Render still requires the merchant’s configured key and verified sender.

## Delivery address book

Checkout remembers a successfully created order’s address by default, in the same database transaction as order creation. The customer can uncheck **Save this delivery address for my next checkout**. The selector explicitly offers **Enter a new address** plus saved destinations; it does not silently choose a destination or submit an outdated quote. Choosing an address fills editable fields and invalidates any existing delivery/tax quote. Country and cart currency are still checked by the normal checkout policy.

**Account → Delivery addresses** lists up to ten saved destinations, allows removal and a default, and can use an existing entry as the template for a new version. Identical normalized addresses are deduplicated. If the address book is full, checkout still succeeds without adding another entry. Address-book changes never alter existing order shipping snapshots, payment state, waybill/tracking details or fulfillment. Address APIs are scoped to the signed-in account; a partial default change and a concurrent checkout use the same transactional per-account lock. Saved addresses contain personal data and are ordinary protected account records, not part of support E2EE.
